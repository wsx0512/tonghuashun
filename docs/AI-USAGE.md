# AI 使用与验证记录

本文件按要求说明：使用了哪些 AI 工具、AI 参与哪些环节、以及在哪些地方
**AI 给出了错误或不合理的结果、由候选人识别并修正**。

后者是本文件的主体——因为「AI 写了什么」没有信息量，「AI 错在哪、怎么发现的」才有。

---

## 1. 使用的工具与分工

| 工具 | 用途 |
|---|---|
| Claude Code（Claude Sonnet 5.5） | 主要编码助手：脚手架、模块实现、测试骨架、文档起草 |
| 人工 | 架构决策、接口契约核实、缺陷判定、取舍与删改 |

**贯穿始终的一条纪律**：AI 生成的每一个与扶摇接口有关的字段名、参数名、错误码，
都以 `https://fuyao.aicubes.cn/llms-full.txt`（465KB 官方聚合文档）为准逐条核对，
不采信 AI 的记忆。凡本文件中标注「已核实」的，都是实际抓取文档确认过的。

---

## 2. AI 参与且**保留**的部分

- 项目脚手架：npm 脚本、tsconfig、Vite 配置、目录结构。
- 测试骨架的**结构**（describe/it 的组织方式、断言覆盖面）。
  但**断言的期望值**全部经过人工判断——AI 写的期望值错了好几处（见下）。
- 部分文案的中文措辞，经人工修订。
- `docs/TESTS.md` 与 README 的初稿结构，经人工重写与补充。

## 3. AI 的错误与修正（主体）

每一条都是实际发生的：AI 先给出了错误方案，候选人通过核实文档、
写测试、或端到端运行发现问题并修正。

### 3.1 把 HTTP 200 当作业务成功 ★ 最严重

**AI 写的**：适配器用 `if (res.ok) { 解析 body }` 判断成功。

**问题**：扶摇 API 的**HTTP 状态码恒为 200**，业务错误藏在响应体 `code` 字段里。
实测确认：

```
无 key 调用     → HTTP 200 + {"code":2003,"message":"Missing X-api-key","data":null}
不存在的路径    → HTTP 200
```

这意味着认证失败、限流、上游宕机**全部会被静默当成成功**，进而把「没拿到数据」
误报成「条件未触发」——直接违反题目「不得静默生成正常结论」。

**修正**：新增 `src/server/sources/envelope.ts` 作为**全系统唯一的解包入口**，
`code !== 0` 一律抛结构化错误。并补回归测试 `TC-C5`
（HTTP 200 + 网关 HTML 错误页 → 必须判为 `MALFORMED_ENVELOPE`）。

**这条也是后续三值逻辑设计的起点。**

### 3.2 选了「未开放外部接入」的能力做数据源 ★ 影响架构

**AI 写的**：事件条件走 `/api/news/events/search`（资讯事件库），
热度条件走 `/api/a-share/capital-flow/*`（主力资金）。

**问题**：核实文档发现，扶摇有 **8 个能力标注「该能力暂未开放外部接入」**，
上述两个正在其中（该措辞在文档中出现 8 次，已逐一定位归属）。

**修正**：事件条件改道到**仍然开放**的端点——异动解读、异动监控、龙虎榜、涨跌停池。
这 8 个能力保留在代码里并显式标注，用作 `CAPABILITY_DENIED` 降级场景的**真实依据**，
而不是凭空捏造失败场景。

**教训**：照着端点清单做设计，可能写完适配器才发现调不通。契约文档里的"限制说明"
和端点清单同等重要。

### 3.3 降级时默认返回 false（"未触发"）

**AI 写的**：`catch (e) { return { matched: false } }`。

**问题**：这正是「静默生成正常结论」——数据没取到，却告诉用户"条件未满足"。
用户会以为监控正常工作，实际上任务已经瞎了。

**修正**：改为 Kleene **三值逻辑**，每个条件返回 `true | false | 'unknown'`，
任务级只要结果是 unknown 就进 `DEGRADED`，**绝不塌缩为 false**。
补测试 `TC-C10`（`AND(T,U)=U`、`OR(T,U)=T`、`NOT(U)=U`）与
`TC-C11`（组合中一个叶子降级、其余为真 → 整体仍 unknown）。

### 3.4 把龙虎榜的 `change` 当成百分数

**AI 写的**：直接拿 `dragon-tiger-list` 的 `change` 字段与价格的
`price_change_ratio_pct` 比较。

**问题**：两个端点的**同义字段口径不同**（已核实）——龙虎榜的 `change` 是**小数**
（`0.067927` 表示 +6.79%），而价格端点的 `price_change_ratio_pct` **已是百分数**。
不归一化就比对会产生 **100 倍的假冲突**，让任务无谓降级。

**修正**：新增 `src/shared/units.ts` 做显式归一化，
并写 `TC-C8` 断言"不归一化会假冲突、归一化后一致"。

### 3.5 臆造字段名

**AI 写的**：用了 `change_pct`、`rank_heat` 等看起来合理但**不存在**的字段名。

**问题**：契约里真实字段是 `price_change_ratio_pct`、`heat` 等。臆造的字段名会让
适配器在真实数据下静默返回 undefined，然后被第 3.3 条的错误处理变成"条件未满足"。

**修正**：字段名逐个对照 `docs/fuyao-contract.md` 核实，并让 fixture 采用**真实字段名**，
使适配器测试能起到断言作用。

### 3.6 组合条件误报"条件已解除"

**AI 写的**：修改规则后，把旧条件的状态当成新条件的状态，发出了"条件已解除"通知。

**问题**：用户把阈值从 1300 改成 9999，那是**另一个条件**——旧条件可能仍然成立，
说"已解除"是误导。

**修正**：条件运行时状态以 `(task_id, leaf_id)` 为键，规则版本变化会改变 leaf 身份，
因此新版本的条件从未为真过，不会误发解除通知。
补测试：**「改规则版本不应触发"条件已解除"」**。

### 3.7 去重与冷却撞在一起，冷却分支成了死代码

**AI 写的**：分桶键和冷却时长都从同一个 `policy.cooldown` 推导。

**问题**：两者粒度永远相同（6 小时冷却 → 6 小时分桶），于是"同一桶内已触发"
总是先于"冷却中"命中，**冷却分支实际从未被执行**。

**修正**：解耦成两个独立的节流器——分桶键按**条件类型**（价格/事件/热度按自然日，
日历按月），冷却时长按任务策略。补测试验证两条分支都可达。

### 3.8 文案含 double negative 与 markdown 残留

**AI 写的**：「未不低于阈值 5.00%」、「本次无法判定——这\*\*不等于\*\*条件未满足」。

**问题**：双重否定难以阅读；markdown 星号会原样显示在界面上。

**修正**：条件未满足时直接陈述**实际方向**（「高于阈值 5%」），去掉所有 markdown 标记。
这是端到端运行时肉眼发现的。

### 3.9 半成品代码留在实现里

**AI 写的**：`engine.ts` 里留了一行无意义的占位代码
（`const thscode = 'subject' in ... ? '' : task.id;`），以及一个绕来绕去的日期计算。

**修正**：代码审查时清除，并把 `alignToTradingHours` 重写为清晰的分支。

### 3.10 部署方案推荐了在国内不可用的工具

**AI 建议**：用 `cloudflared` 做公网隧道。

**问题**：**实测其 GitHub release 二进制在国内下载失败**；
`winget install Cloudflare.cloudflared` 也同样失败（走同一个 CDN）。
备选方案 `localtunnel` 虽然能装，但它对浏览器请求会插入一个**要求输入密码的中间页**，
评审打开链接会先撞上这个，体验不可接受。

**修正**：改用系统自带的 `ssh -R` 隧道（无需下载任何东西，无中间页），
并**把这一步提到排期的第一件事**——先打通部署链路再写代码。
如果留到最后才发现，就来不及了。

### 3.11 冒烟测试的"故障注入"时灵时不灵

**AI 写的**：故障注入的"数据过期"固定把数据时点推回 3 小时。

**问题**：新鲜度策略在**闭市后会放宽阈值**（收盘后的价格数据本就该是几小时前的），
所以固定推回 3 小时在某些时段会落在阈值之内——**"注入过期"却判为新鲜**，
演示时灵时不灵。这是端到端运行才暴露的。

**修正**：默认值改为「该端点**当前生效的阈值** + 1 小时」，保证任何时刻都真的过期。

### 3.12 演示用的故障注入作用域过窄，点了没反应

**AI 写的**：各故障场景绑定到"合理"的窄作用域
（如"数据未就绪"只作用于异动/热榜端点）。

**问题**：从演示面板点击时，用户正在看的可能是价格任务——点了**毫无反应**，
演示直接砸掉。

**修正**：从 API/界面触发的故障注入**默认作用于所有端点**，
需要精准打击时显式传 `endpoints`（冒烟测试与单元测试就是这么用的）。

### 3.13 测试断言本身写错

**AI 写的**：
- 断言 `近20日累计涨幅大于1%` 的阈值是 `1`，但解析器实际给出 `20`——
  **这条断言暴露的是真 bug**（数字提取器抓到了窗口里的数字，已修）。
- 断言某个"次日"场景，但时间只推进了 2 小时就期望跨桶。
- 断言"重启后不重复通知"，却用了会共享内存的连接，测不出重启语义。

**修正**：逐条人工判断——**哪些是测试写错了、哪些是被测代码错了**。
第 3.13 条的第一项属于后者，正是测试的价值所在。

### 3.14 把回放数据标成"实时"（虚假来源标注）★ 性质最恶劣

**AI 写的**：`SENTINEL_MODE === 'live'` 时，`/api/meta` 返回
`dataSource: '扶摇 API（实时）'`、`dataSourceNote: '通过 X-api-key 调用 fuyao.aicubes.cn'`；
README 还写了「设 `SENTINEL_MODE=live` 即可切换实时数据」。

**问题**：代码里**根本不存在实时适配器**。`src/server/sources/` 下只有 `replay` 与
`chaos`，全服务端没有任何出站 HTTP；`SENTINEL_MODE` 被读取的三处**全都是显示文案**。
于是设了这个环境变量，系统会把**回放数据标成实时数据**。

这不是普通 bug，它直接**伪造了本作品的立身之本**：本项目全部说服力都建立在
"数据来源如实标注、不确定就说不确定"之上，而这个分支让评审在**假前提下**核对这个主张。
更糟的是冒烟测试的来源断言写成 `/回放|实时/.test(...)`，**两种值都通过**，所以没有任何测试会拦它。

**修正**：
- 删除环境变量驱动的标签。`/api/health` 的 `mode` 与 `/api/meta` 的 `dataSource`
  改为来自 `AppContext.dataSource`，即**实际装配的适配器**的描述（描述"实际发生了什么"，
  而不是"用户想要什么"）。
- 设 `SENTINEL_MODE=live` 时打印明确告警，说明实时适配器未实现、仍用回放、且会如实标注。
- 冒烟测试新增两条断言：`mode === 'replay'`，以及 health 与 meta 两个接口**口径自洽**。
- README 的"切换真实数据"一节改为"**尚未实现**（如实说明）"，并说明已实现的是契约层
  （信封解包 + 13 个错误码语义 + 端点表），未实现的是 HTTP 传输层。

**这条也是"人做取舍"的例证**：修法有两种——把标签改诚实，或者真去实现实时适配器。
选了前者，因为**没有 Key 就无法验证连通性**，写了也只是未经执行的网络代码。

### 3.15 契约核对不彻底：臆造字段残留，量比条件实际不可用

**背景**：第 3.5 条声称已"逐个对照契约核实字段名"。2026-10-16 用存档的契约原文
（`docs/fuyao-contract.md`）重新逐字段核对，发现**修正不彻底**，残留四类问题：

| 代码读取 | 契约实际 | 后果 |
|---|---|---|
| `volume_ratio`（快照） | `PriceSnapshotItem` **无此字段**；契约里只有另一个端点的 `auction_volume_ratio` | **量比条件永远无法判定** |
| `tag_code`（异动响应） | 响应字段是 `tag_name`；`tag_codes` 是**请求**参数 | 按标签过滤永远不命中 |
| `billboard_net_amt` | 契约中**零次出现**；龙虎榜净买入是 `net_value` | 净额过滤永远不命中 |
| 龙虎榜取 `data.item` | 契约返回 `data.stock_items` | 真实数据下取到空数组 |

**最严重的是量比**，因为它是**对外宣传的功能**：README 的价格指标表列了"量比"，
中文词典也有「放量/量比超过/量比大于」。实测（`POST /api/rules/parse` 解析
「贵州茅台量比超过2」→ 建任务 → 立即评估）：

```
truth       : unknown
state       : PENDING -> DEGRADED
leaf.reason : EMPTY_DATA
observations: 0
```

即：**这个功能从上线起就没工作过**。已实现的是"取快照里的 `volume_ratio` 字段"，
但扶摇快照根本不提供它。

**已修正（2026-10-16）**：

| 问题 | 修法 |
|---|---|
| 量比直读快照字段 | 改为**从历史 K 线派生**，与 `drawdown_from_high_pct` 同路（`computeHistorical`）。实测「贵州茅台量比超过1」得 `truth=true`，观测值 2.0283 RATIO，口径「当日成交量 ÷ 近 5 个交易日平均成交量」 |
| `tag_code` 比对响应 | 标签过滤改走**请求参数 `tag_codes`**（契约的真实过滤方式）；回放侧用 `_tag_code_mock` 显式模拟，且**该字段名自带下划线前缀以标明非契约** |
| `billboard_net_amt` | 改名 `net_value`（契约字段名），代码 + fixture + 录制脚本同步 |
| 龙虎榜取 `data.item` | 改取契约的 `data.stock_items`；新增 `listKeyFor()` 统一端点→列表键的映射，并补测「龙虎榜的列表键是 stock_items，不是通用的 item」 |

**值得记下的教训**：三值逻辑在这里**救了场**。这个 bug 的表现不是"错报正常"，
而是老实降级成 `unknown` + `EMPTY_DATA`——因为第 3.3 条把"默认返回 false"改掉了。
**正确的降级设计让一个坏功能表现得像个诚实的坏功能，而不是一个假的正常结论。**
但它同时也说明：**降级正确会掩盖功能缺失**，所以"字段是否真实存在"必须单独核对，
不能只靠降级日志。

**另一个教训**：第 3.5 条当时声称"已逐个对照契约核实"，但**核对不彻底**——
它只核对了当时正在写的那几个字段，没有系统性地把"代码读的每个字段"都过一遍。
真正的修法不是"这次仔细点"，而是**把契约原文存档进仓库**（`docs/fuyao-contract.md`），
让后续每一次核对都有一条可复现的命令，而不是依赖记忆。本条的发现正是这么来的。

## 4. 由测试发现（而非 AI 自述）的缺陷

以下缺陷是**先写了测试，测试跑红，才发现的**。这是"AI 辅助"与
"AI 自主"的分界线——如果没有这些断言，它们会安静地留在代码里：

| 缺陷 | 发现方式 |
|---|---|
| `freshness.ts` 的收盘时刻多减了 8 小时 → 闭市后过期阈值虚高，旧数据被判为新鲜 | 端到端 + 单测断言 `ageMs > threshold` |
| 按 `ticker` 反查标的发生撞车（`000001.SZ` 平安银行 vs `000001.SH` 上证指数） | 测试断言"无重复 thscode" |
| 历史 K 线契约里 `thscode` 在 `data` 层而非 `item` 上，按 item 查找永远找不到 | 评估器测试返回 `EMPTY_DATA` |
| 词典按数组顺序匹配导致 `超过` 抢在 `涨幅超过` 之前命中 | 测试断言 `>=` 得到 `>` |
| 冲突检出后仍给出肯定结论 | 端到端冒烟测试断言 `truth === 'unknown'` |

## 5. 验证方式

1. **契约核实**：所有扶摇相关字段名、参数、错误码，对照 `llms-full.txt` 逐条核对。
   已抓取的契约存为 `docs/fuyao-contract.md`。
2. **单元/集成测试**：`npm test`，160 个用例。
3. **端到端冒烟**：`npm run smoke`，30 项检查，对着**运行中的服务**跑完整主链路，
   并把用户实际会看到的中文文案打印出来核对。
4. **故障注入手工复现**：在「演示与破坏」面板逐一点击各场景，
   核对降级原因与中文解释是否符合预期。
5. **真实数据对照**：fixture 的数值与东方财富/新浪公开行情逐项对照
   （如贵州茅台 2026-10-15 收盘 1312.97 元、跌幅榜数据等）。
6. **合规穷举**：`allTemplateSamples()` 把模板库所有形态渲染一遍并做违规扫描，
   将来任何人往模板里加一句「预计上涨」，测试会立刻变红。

## 6. 结论

AI 在本项目中显著提速了**结构化的工作**——脚手架、测试组织、文档骨架、
重复性的适配器代码。但它在三类事情上不可靠，且这三类恰好都是要命的地方：

1. **外部契约的细节**（字段名、口径、能力可用性）——它会用记忆填补空白。
2. **失败路径的语义**——它倾向于返回一个"看起来正常"的值，而不是承认不知道。
3. **跨模块的不变量**——它能写出每个模块，但不会主动发现"这两处的口径其实不一致"。

因此本项目的实际工作方式是：**AI 写，测试判，人做取舍**。
本文件里 15 条错误，没有一条是 AI 自己发现的。
