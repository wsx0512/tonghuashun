# 测试说明

题目要求测试至少覆盖**主链路、数据缺失/接口失败、合规边界**三类场景。本文件说明
测试的组织方式、每个用例的意图，以及**为什么某些看似奇怪的地方必须被断言**。

```bash
npm test        # 160 个单元/集成测试（Vitest）
npm run smoke   # 28 项端到端检查，需服务已启动
```

## A 组 · 主链路

### 自然语言 → 规则（`parser.test.ts`）

| 用例 | 断言 |
|---|---|
| `贵州茅台跌破1200元` | `last_price < 1200`，标的解析为 `600519.SH` |
| `贵州茅台涨幅超过5%` | `price_change_ratio_pct >= 5` |
| `贵州茅台跌超3%` | 语义是"下跌"，值取负：`<= -3` |
| `宁德时代回撤超过10%` | `drawdown_from_high_pct` |
| `比亚迪近20日累计涨幅大于15%` | `return_pct_window`，`window.days = 20` |
| `贵州茅台跌破一千二百元` | 中文数字解析为 1200 |
| `A 或者 B` / `A 并且 B` | OR / AND 节点 |
| `(A 或 B) 并且 C` | **括号改变默认优先级**，树形为 AND(OR(A,B), C) |
| `贵州茅台出现涨停` | 事件源必须是**可用端点**（`limit_up_pool`），**不能**是 `news_events_search` |
| `连续2天涨停` | `filter.minContinueDayCnt = 2` |
| `进入热榜前10` | `heat.in_top_n`，值 10 |
| `每个交易日` | 日历条件 |

### 规则求值（`evaluate.test.ts`）

覆盖四类条件的**命中与未命中**两条路径，且特别断言一条容易搞错的语义：

> **"不在池中"是有效的业务事实，不是未知。**

「贵州茅台今天没涨停」应当判为 `false`（今天是涨停池的完整清单，不在其中就是没涨停），
而**不是** `unknown`。但如果查一个标的价格却查不到，那必须判 `unknown`
（拿不到数据 ≠ 数值为零）。这两种情况在 `dataNeeds.ts` 里用
`MEMBERSHIP_ENDPOINTS` 明确区分。

## B 组 · 调度与状态

| 用例 | 意图 |
|---|---|
| 同一时间槽重复调用只评估一次 | 调度幂等（`runs` 表 UNIQUE 约束） |
| 时钟推进后可再次评估 | 幂等不是"永不重复" |
| 同桶内二次命中被抑制且不留第二条通知 | 去重生效 |
| 跨桶可以再次触发 | 去重不是"永不触发" |
| bucketKey 按条件类型分桶，与冷却时长无关 | **守护去重与冷却的解耦**（见下） |
| 冷却期内条件为真 → 抑制并计数 | 冷却生效，且用户可见 |
| edge 模式：条件持续为真时不重复通知 | 边沿触发 |
| 条件由真转假 → 发出"条件已解除" | 条件级恢复 |
| **改规则版本不应触发"条件已解除"** | 换了阈值就是另一个条件，不能谎称"已解除" |
| 降级后数据恢复 → 健康恢复通知（含降级时长） | 健康级恢复 |
| 连续失败达阈值 → FAILED | 失败计数 |
| 冷启动把中断的 run 标记为 interrupted | 崩溃恢复 |
| 去重键持久化，重建 deps 后仍生效 | 跨重启去重 |
| 规则版本递增且历史保留 | 版本留存 |
| 评估结果绑定当时的规则版本 | 可解释"昨天为什么没触发" |
| `dailyAt` 在非交易日顺延 | 交易日历感知 |
| `tradingHoursOnly` 收盘后顺延到次日开盘、午休顺延到 13:00 | 交易时段感知 |
| 状态变化写入 events 表 | 状态变迁可追溯 |

### 为什么「去重与冷却解耦」值得一条专门的断言

早期实现里，分桶键和冷却时长都从 `policy.cooldown` 推导。结果两者粒度永远相同：
6 小时冷却 → 6 小时分桶，"同一桶内已触发"**总是先于**"冷却中"命中，
**冷却分支从未被执行过**——是死代码，但行为看起来"正常"。

现在分桶键按**条件类型**（价格/事件/热度按自然日，日历按月），
冷却时长按任务策略。这条断言守护的就是二者不再耦合。

## C 组 · 数据缺失、接口失败与降级

### 响应信封（`envelope.test.ts`）★

| 用例 | 断言 |
|---|---|
| **`TC-C1`** `code=2003` | 判为 `CAPABILITY_DENIED`，**不是**"成功但没数据"；文案含「不会给出正常结论」 |
| **`TC-C2`** `code=4001` / HTTP 429 | `RATE_LIMITED`，可重试，文案含「不会被误判为未触发」 |
| **`TC-C3`** `code=3002` | `NOT_READY`，文案必须说明"**不等于**没有发生" |
| **`TC-C4`** `code=5003` | `FAILURE`，可重试 |
| **`TC-C5`** HTTP 200 + 网关 HTML 错误页 | `MALFORMED_ENVELOPE` |
| **`TC-C5b`** 信封缺少数值型 `code` | `MALFORMED_ENVELOPE` |
| **`TC-C5c`** HTTP 500（body 却是成功信封） | `FAILURE` —— 不能只看 body |
| `code=0` 但 `data=null` | `EMPTY_DATA` |
| `code=1002` 参数错误 | `UNSUPPORTED`，**不可重试**（重试没意义，要改规则） |
| **`TC-C6`** `data.timestamp` 超阈值 | 判为不新鲜，说明含时点与阈值 |
| `data.timestamp` 缺失 | **不得默认当作新鲜** —— 这是最容易漏的一条 |

> **`TC-C5` 是本项目最重要的一个测试。** 它守护的是「HTTP 200 不等于业务成功」。
> 一旦有人把 `unwrapEnvelope` 换成 `if (res.ok)`，这个用例会立刻变红。

### 故障注入与冲突（`adapters.test.ts`）

| 用例 | 断言 |
|---|---|
| `upstream_failure` / `rate_limited` / `capability_denied` / `malformed` | 各自落到预期原因码 |
| **`TC-C6`** `stale_price` | 数据**取到了**但时点被推旧，且 `ageMs > 当前生效阈值` |
| **`TC-C9`** `partial_null` | 金额字段置为 `null`，**断言不是 0** —— 补零会把"没有数据"伪装成"金额为零" |
| 场景作用域 | 不匹配的端点不受影响 |
| `clear()` 后恢复正常 | 故障可撤销 |
| `TC-C7` 两源偏差 0.87% | 检出冲突，**两个值都保留**，主源数值不被备源替换 |
| 偏差在阈值内 | 不报冲突（避免浮点噪声造成假冲突） |
| 备源失败 | **不污染主源结果**，只降级为"无冲突检测" |
| **`TC-D5`** 龙虎榜 `EXPLAIN` 含「成功率44.94%」 | 适配器**必须丢弃**该字段；断言输出中不含「成功率」「44.94」 |
| 净化不影响数值字段 | 数据结构完整 |

### 单位口径（`TC-C8`）★

龙虎榜的 `change` 是**小数**（`0.067927` = +6.79%），
价格的 `price_change_ratio_pct` **已是百分数**。测试同时断言两件事：

1. 直接比较会产生 >50% 的**假冲突**
2. 归一化后两者一致

**这是真实契约里的坑，不是假想。** 不处理会让任务无谓降级。

### 三值逻辑（`evaluate.test.ts`）★

| 用例 | 断言 |
|---|---|
| 数据获取失败 | `truth === 'unknown'` 且**断言 `!== false`** |
| **`TC-C10`** `AND(true, unknown)` | `unknown` |
| **`TC-C10`** `OR(true, unknown)` | `true`（一支为真即可定论） |
| **`TC-C11`** 组合中一个叶子降级、其余为真 | 整体仍 `unknown`，**不得塌缩为 true** |
| **`TC-C7b`** 源冲突 | 判为 `unknown`，两个取值都保留在证据里 |

## D 组 · 合规边界

### 意图拒绝（`parser.test.ts`）

8 条输入逐条断言被拒绝、给出 `complianceLabel`、且**不产出任何规则**：

```
茅台会涨吗 / 茅台什么时候买入 / 现在要不要卖宁德时代 / 贵州茅台能涨到多少
给我推荐一只股票 / 茅台的止盈位是多少 / 应该买茅台吗 / 茅台能赚多少
```

拒绝话术还要说明**产品能做什么**（「可以试试这样说：贵州茅台跌破 1200 元时提醒我」），
而不是干巴巴地说"不行"。

### 能力边界 —— 诚实报告"做不到"

| 用例 | 断言 |
|---|---|
| `贵州茅台走势健康` | 判为 `no_condition`，说明"主观描述无法转成客观条件"，**并给出可替代的说法** |
| `跌破1200元`（无标的） | 提示补充标的 |
| `关注一下贵州茅台`（无条件） | 提示给出明确条件 |
| `000001`（裸代码） | **报告歧义**（平安银行 or 上证指数），不猜 |
| `000001.SZ` / `000001.SH` | 按市场后缀正确区分 |

### 模板与过滤器（`compliance.test.ts`）

| 用例 | 断言 |
|---|---|
| **`TC-D2`** 模板库**全部形态**穷举渲染 | 逐条扫描，零违规 |
| 事实型文案不含将来时 | 正则断言 |
| 结论句不含祈使句买卖建议 | 正则断言 |
| **`TC-D3`** 8 条越界文案 | 逐条被拦下（「预计将上涨」「建议买入」「目标价」「上涨概率为 80%」…） |
| `assertCompliant` 抛错并携带违规明细 | 运行期守卫有效 |
| 合法事实陈述不被误伤 | 反向断言，避免过滤器过严 |
| **`TC-D6`** 降级文案 | 必含「无法判定」，且**不出现**「未触发」「正常」 |
| 恢复文案 | 只陈述"已解除"，不暗示后续走势 |

> **穷举渲染的意义**：将来任何人往模板里加一句「预计上涨」，
> CI 会立刻变红，而不是等到评审看到那句文案。
> 这正是"强制"与"自觉"的分界。

## F 组 · 站外推送投递（`webhook.test.ts` / `engine.test.ts`）

守护的是一个**特别容易造成误导**的失败模式：任务触发了、通知也生成了，
但用户根本没收到，而系统看起来一切正常。所以每条失败路径都必须有明确状态。

| 用例 | 断言 |
|---|---|
| 未配置渠道 | 返回 `SKIPPED`，且 **`fetch` 一次都没被调用**——不是"发失败了"，是"根本没发" |
| 空白 URL | 等同于未配置，而不是"配置了一个空地址" |
| 2xx 送达 | `SENT`、`attempts=1`；payload 带 `epistemic` 与合规声明 |
| 500 后重试成功 | `SENT` 且 `attempts=2`（证明真的重试过，不是假装） |
| 重试耗尽 | `FAILED`，尝试次数用满，错误里带 HTTP 状态原文 |
| 网络异常 | `FAILED`，错误保留 `ECONNREFUSED` 之类的**原始原因**，不吞成"未知错误" |
| 超时 | 单列为「超时」，而非含糊的网络错误 |
| ★ 文案含禁用词 | `SKIPPED`，且**一个请求都不发**（宁可拒发，也不发出去） |
| ★ 数据源夹带「成功率44.94%」 | 同样被拦下 |
| `describe()` | 不泄露 URL 上的 `?token=` 凭据 |
| 引擎：未注入渠道 | 通知照常生成，投递如实记为 `SKIPPED` 并写明原因 |
| 引擎：注入渠道 | 记为 `SENT`，投递内容与通知一一对应，任务名随件送出 |
| 引擎：渠道抛错 | **tick 不崩**，但失败留痕（`last_error` 含原始信息） |
| 重复投递同一通知 | **更新**原记录，不追加重复行 |

## 契约对齐断言（`evaluate.test.ts`）

请求参数与响应字段必须落在契约定义的名字上。这类 bug 在回放模式下**完全看不出来**
（回放忽略除 `thscode` / `thscodes` 外的参数），只有真实调用才会报 `code=1001`——
所以只能对着契约文本写断言。

| 用例 | 断言 |
|---|---|
| 历史 K 线 | 发 `start` / `end`；**不发**契约里没有的 `days`；`end > start` |
| 窗口夹紧 | 窗口天数设成 99999 时，跨度仍被夹在 10 年以内（契约 `code=1003` 的界限） |
| 热榜走势 | 发 `thscode` + `yyyy-MM-dd` 的 `start_date` / `end_date`；**不发** `period` |
| 按股票查异动 | 发复数 `thscodes`；**不发**单数 `thscode` |
| 清单类端点 | 涨跌停池 / 龙虎榜 / 异动监控的参数里**不含**任何 thscode |
| 收窄参数后仍能定位 | 去掉查询参数后，评测器在完整清单里仍能按 thscode 找到标的（客户端过滤兜底） |
| 量比来源 | 走 `prices/historical` 派生，而不是读快照里不存在的 `volume_ratio` |
| 龙虎榜容器 | 列表取自 `data.stock_items`（不是通用的 `data.item`） |
| 龙虎榜净额过滤 | 读契约字段 `net_value` |
| 异动标签 | 走请求参数 `tag_codes`，而不是比对响应里不存在的 `tag_code` |

**另有一条关于"编造数字"的修正**：事件 / 热度 / 日历类的证据时效曾被写死为
`ageMs: 0, fresh: true`，实际从未测量。现已改为就地测量真实年龄，
并在数据确实偏旧时于界面上一并给出"为什么不因此降级"的说明。

## 端到端冒烟测试（`npm run smoke`）

31 项检查，对着**运行中的服务**跑完整主链路，并打印用户实际会看到的中文文案：

```
① 服务健康         健康检查、交易日历加载、数据来源标注
② 自然语言 → 规则   组合条件、括号优先级
③ 合规边界         3 条预测/建议输入被拒
④ 能力边界         主观描述被拒且给出替代说法
⑤ 主链路           创建任务、触发、证据链六要素
⑥ 降级             过期 → 无法判定 + 不产生触发通知
⑦ 恢复             恢复正常 + 健康恢复通知
⑧ 源冲突           两值并列 + 不给肯定结论
⑨ 接口失败         5 种故障码逐一验证
```

**为什么单独做冒烟测试**：单元测试验证各模块的确定性行为，
但"装配起来能不能用"是另一回事。本次开发中，**故障注入作用域过窄**
（从演示面板点击无反应）就是冒烟测试发现的，单元测试全绿也照样漏。

## 已知的测试缺口

诚实列出没测到的地方：

1. **真实扶摇数据未测**。没有 API Key，无法验证适配器在真实响应下的行为。
   适配器按契约实现，fixture 采用真实字段名与信封结构，但"契约正确"与
   "真实实现与我理解的一致"是两回事。
2. **并发未测**。当前是单进程单 tick，未做多实例并发下的幂等验证。
3. **前端无自动化测试**。界面靠手工走查与冒烟测试间接覆盖，
   没有组件测试或端到端浏览器测试。
4. **长时间运行未测**。调度器跨天、跨周的漂移未经验证（测试用注入时钟模拟）。
5. **时区边界未充分测**。仅覆盖了 `Asia/Shanghai`，未测夏令时（A 股无夏令时，但代码未显式防御）。
