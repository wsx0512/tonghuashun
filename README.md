## 快速开始

**无需任何 API Key。** 默认使用确定性回放数据。

```bash
npm install
npm run seed      # 载入 6 个演示监控任务
npm run start     # 构建前端并启动服务
```

打开 **http://localhost:8787**。

进界面后：

1. 顶部输入框写一句话 → 点【解析】→ 核对解析结果 → 【保存为监控任务】
2. 任务卡片点【立即评估】看到结论与证据链
3. 切到「演示与破坏」页，点【数据过期】→ 回「监控任务」看降级解释
4. 点【恢复正常】→ 收到恢复通知

其他命令：

```bash
npm test          # 180 个单元/集成测试
npm run smoke     # 端到端冒烟测试（需服务已启动），31 项检查
npm run typecheck # 类型检查
npm run record    # 重新从公开行情源生成 fixture（可选）
```

### 公网访问

服务是单个长驻 Node 进程（调度器必须在长驻进程里跑，所以 Serverless 不适用）。
用任意隧道工具暴露即可：

```bash
# 方案 A：系统自带 ssh，无需下载
ssh -R 80:localhost:8787 nokey@localhost.run

# 方案 B：cloudflared（国内需从镜像获取二进制，或用 winget）
cloudflared tunnel --url http://localhost:8787
```

> 注：`localtunnel` 也能用，但它对浏览器请求会插入一个要求输入密码的中间页，
> 评审体验不好，故未采用。

## 产品与目标用户

**哨兵 Sentinel** 是面向**个人投资者**的可配置监控与风险雷达。

目标用户的处境很简单：有十来个自选股，想盯住几个关键点，但没精力一直看盘。
他们脑子里的关注点是自然语言——「跌破 1200 提醒我」「上热榜了告诉我」——
而不是指标公式或代码。

现存工具的问题不是不能设条件，而是**设完之后不知道它在干什么**：
任务真的在跑吗？今天为什么没提醒？是没到条件，还是数据根本没取到？
哨兵把「解释清楚」当成一等功能。

**核心用户旅程**

| 步骤 | 用户做什么 | 系统做什么 |
|---|---|---|
| 1 | 说人话 | 解析成结构化条件，**把没解析出来的部分也告诉他** |
| 2 | 核对并修改 | 逐条展示条件，可编辑阈值、切换 AND/OR |
| 3 | 保存 | 生成规则 v1，纳入调度，交易日历感知 |
| 4 | 回来看 | 状态徽章 + 下次评估时间 + **为什么触发/没触发** + 证据链 |
| 5 | 看全局 | 风险雷达按「维度 × 状态」聚合，**降级任务是醒目的盲区** |

## 核心设计

### 1. 统一规则模型

一套模型统一题目要求的四类条件 + 逻辑组合，可在界面上逐条检查和修改。

| 类型 | 表达 | 数据来源 |
|---|---|---|
| **价格** | 最新价 / 涨跌幅 / 区间累计涨幅 / 回撤 / 量比 / 成交额 | `prices/snapshot`、`prices/historical`、`valuations/snapshot` |
| **事件** | 涨停 / 跌停 / 炸板 / 连板 / 龙虎榜 / 异动 / 监控名单 | `special-data/*` |
| **热度** | 热榜排名 / 排名变化 / 进入前 N | `special-data/hot-stock-list` |
| **日历** | 是否交易日 / 本月第 N 个交易日 / 距新股申购 | `calendar/trading-days`、`ipo/calendar-list` |
| **组合** | AND / OR / NOT，支持括号改变优先级 | — |

叶子节点**不直接调用数据源**，而是声明「我需要哪份数据」。这一个决定同时带来三件事：
用户能看见每条规则会去打哪些接口；同一 tick 内多个任务的相同请求可以合并成一次调用；
某个接口失败时能精确定位受影响的条件。

**「可检查」是两层校验**：Zod 严格模式（拒绝未知字段、枚举越界）+ 跨字段语义校验
（算子与单位是否匹配、标的类型是否支持该指标、窗口是否越界、是否会长期降级）。
输出分 errors（阻断保存）与 warnings（允许保存但必须告知）。

**「可修改」**：每次保存生成新版本并保留历史，旧版本不可回改。
每条评估结果绑定当时生效的版本号——所以「昨天为什么没触发」可以精确回答。

### 2. 自然语言 → 规则

确定性中文解析器，不是模型。

这不只是因为拿不到 LLM Key，更是因为题目要求规则**可检查、可修改**：
确定性解析器让用户看到的就是系统真正理解的东西。而且它能诚实说「这句我解析不了」，
模型则倾向于猜一个看起来合理的规则。

- **承诺支持**（有单测）：价格阈值、涨跌幅、回撤、区间累计涨幅、放量、涨停跌停炸板连板、
  龙虎榜、异动、监控名单、热榜排名、交易日历、AND/OR 与括号组合、中文数字（「一千二百」）
- **明确不支持并如实告知**：主观描述（「走势健康」）、需要新闻语义的开放事件、嵌套超过 3 层
- **直接拒绝**：预测与建议类意图（「会涨吗」「什么时候买」「推荐一只股票」）

界面把**未识别的片段**用橙色显式列出——这是诚实边界，也是"可检查"的第一步。
LLM 增强插槽保留但默认关闭，且其输出**仍必须通过同一套校验**才被接受。

### 3. 降级：本作品的重点

题目对降级的要求可以概括成一条：

> 数据缺失、冲突、过期或调用失败时**不得静默生成"正常"结论**。

这句话在代码里落地为**三值逻辑**。

每个条件返回 `true | false | unknown`，组合走 Kleene 三值逻辑：

| AND | T | F | U |  | OR | T | F | U |
|---|---|---|---|---|---|---|---|---|
| **T** | T | F | U |  | **T** | T | T | T |
| **F** | F | F | F |  | **F** | T | F | U |
| **U** | U | F | U |  | **U** | T | U | U |

`NOT U = U`。**任务级：最终结果是 unknown 就进 DEGRADED，绝不塌缩为「未触发」。**

直觉是：AND 里一个 F 足以定论（即使另一支未知）；OR 里一个 T 足以定论。
只有真正定不下来时才承认"不知道"。

> 早期实现里，AI 生成的代码在取数失败时默认返回 `false`（"未触发"）。
> 这正属于"静默生成正常结论"，被改成三值逻辑后才合规。

#### 四类降级 + 一个陷阱

| 场景 | 判定 | 用户看到的话 |
|---|---|---|
| **数据过期** | 数据时点超过该端点当前生效的阈值 | 「数据时点为 13:30，距今 416 分钟，超过阈值 6 小时。本次**无法判定**——这不等于条件未满足。」 |
| **源冲突** | 主备源同字段相对偏差 > 0.5% | 「数据源冲突：fuyao=1312.97 与 backup=1324.39 相差 0.86%。」**两个值并列展示，不静默二选一** |
| **接口失败** | `code ∈ {5001,5002,5003}` / 超时 / 非标准响应 | 「上游异常（code 5003）。本次无法取得数据，该条件无法判定。」 |
| **限流** | HTTP 429 或 `code=4001` | 「已按退避策略延后重试，不会被误判为未触发。」 |
| **能力未开放** | `code=2003` | 「该数据能力未开放外部接入，相关条件已暂停评估。」 |

**HTTP 200 陷阱**：扶摇 API 的所有业务响应 **HTTP 状态码恒为 200**，
业务错误藏在响应体的 `code` 字段里。实测无 key 调用返回
`{"code":2003,...}` 且 HTTP 200，访问不存在的路径同样返回 HTTP 200。

这意味着任何 `if (res.ok)` 的写法都会把「认证失败」「限流」「上游宕机」
**静默当成成功**，进而把"没拿到数据"误报成"条件未触发"。

全系统**只允许在 `src/server/sources/envelope.ts` 一处解包响应**，
其余任何地方都不得直接读 `code`。对应回归测试 `TC-C5`。

**冲突为什么不给结论**：早期实现里检出冲突后仍按主源取值给出"条件未满足"。
但这是在一个有争议的数字上做出的**肯定断言**，与题目的要求相悖。
现在冲突 → 判为 unknown，两个取值都列在证据里，由用户判断。

### 4. 状态机：调度 · 状态 · 去重 · 冷却 · 恢复

```
DRAFT → PENDING ⇄ PAUSED
           ↓ 评估=true          ↓ 评估=unknown
      TRIGGERED → COOLDOWN        DEGRADED → RECOVERING → PENDING
                                    连续失败 ≥ max ↓
                                  FAILED → RECOVERING
```

三个不变量靠**数据库约束**而非内存状态保证，因此跨进程重启依然成立：

| 不变量 | 实现 |
|---|---|
| **调度幂等**：同一时间槽只评估一次 | `runs(task_id, slot_key)` UNIQUE + `INSERT OR IGNORE` |
| **去重**：同一分桶内只通知一次 | `triggers(dedup_key)` PRIMARY KEY + `INSERT OR IGNORE` |
| **状态变迁留痕** | `events` 表，不可变追加 |

**去重与冷却解耦**（两个不同的节流器）：

- **分桶键**按**条件类型**：价格/事件/热度按自然日，日历按月
  （日历条件每个交易日都命中，按日分桶会把用户淹没）
- **冷却时长**按任务策略：交易日 / 小时 / 毫秒

> 早期实现里两者都从 `policy.cooldown` 推导，导致粒度永远相同、
> **冷却分支实际是死代码**。测试抓到了这个问题。

**被抑制的触发会留痕**（`suppressed` 表），用户能看到"冷却期内本会触发 N 次"，
而不是静默丢弃。

**恢复**分两级：条件级（true→false 发「条件已解除」）、健康级（降级→正常发「数据恢复」
并注明降级时长）。冷启动时把上次进程遗留的 `evaluating` 记录标记为 `interrupted`
并重跑一次（去重键保证不会重复通知）。

**补算标记**：断档后的补算结果标记为 `backfilled`，与实时触发在界面上区分——
不能让补算冒充实时。

### 5. 可追溯性

每条结论都能沿证据链回到原始字段。`EvidenceRecord` 的观测项包含：

| 要素 | 字段 |
|---|---|
| 来源 | `source.provider` / `source.endpoint` / `source.requestParams` |
| 时点 | `dataTimestampMs`（上游 `data.timestamp`，**不是本地取数时刻**） |
| 单位 | `unit`（CNY / PCT / SHARES / CNY_AMOUNT / RANK / DAY） |
| 口径 | `statisticBasis`（如「最近 20 个交易日累计涨跌幅」「距最近 60 个交易日最高价的回撤」） |
| 原始响应 | `source.rawResponseRef` → `raw_responses` 表，可看到完整 JSON |
| 追溯锚点 | `source.requestId`（扶摇信封的 `request_id`） |

界面每条结论都能展开看到这张表，以及比较过程（`lhs op rhs → 通过/未通过`）。

### 6. 合规：强制而非自觉

题目明令不得输出确定性涨跌预测、收益承诺或直接买卖建议；事实、推断与不确定信息必须区分。
分四层强制：

1. **能力层**：自然语言解析遇到预测/建议意图 → 直接拒绝生成规则，留痕到 `compliance_rejects`
2. **生成层**：所有面向用户的结论句**只能由白名单模板生成**，模板不含自由文本槽位，
   因此结构上就写不出违规文案
3. **过滤层**：禁用词表 + 句式正则扫描。命中即**抛错**（构建期测试会拦住），
   而不是静默过滤——静默过滤会让模板缺陷永远查不出来
4. **数据层**：出站数据净化。**真实数据源会附带预测性文字**——东方财富龙虎榜的
   `EXPLAIN` 字段返回 `"普通席位买入，成功率44.94%"`，这是对历史席位的统计外推。
   适配器递归扫描所有字符串字段并丢弃命中者，而不是硬编码字段名

### 7. 站外推送：**未配置这件事本身必须看得见**

一个只在浏览器里弹提示的监控产品，用户关掉页面就等于没监控——「长期运行」也就成了空话。
所以哨兵有站外推送（Webhook）：

```bash
SENTINEL_WEBHOOK_URL=https://your-endpoint.example.com/hook npm run start
```

**默认不配置，也默认不假装配置了。** 没设这个变量时，每条通知仍会生成，但投递记录
如实写成 `SKIPPED` 并注明原因，界面上逐条显示「未配置推送渠道」。

这条设计的理由和降级那一节是同一条：**推送失败是最容易被静默吞掉的一环**——
用户以为「没触发」，其实是触发了但没送出去。所以每一次投递都要有明确去向，三种状态都可见：

| 状态 | 界面显示 | 含义 |
|---|---|---|
| `SENT` | 已推送（重试 N 次） | 2xx 送达；重试过会标出来 |
| `FAILED` | 推送失败（尝试 N 次） | 3 次尝试后仍失败，附最后一次错误原文 |
| `SKIPPED` | 未配置推送渠道 / 内容未通过合规 | **没有发出任何请求**，且写明原因 |

两个额外约束：

- **出站内容再扫一遍合规**。模板层已经扫过，这里刻意重复一次：一旦命中禁用词就
  **拒发**并记为 `SKIPPED`，而不是发出去。纵深防御——模板今天没错不代表将来也不会错。
- **认知等级随消息送出**（`epistemic: fact / inference / unknown`），收端能区分
  「这是已发生的事实」还是「无法判定」，不会把降级误读成正常。

## AI 的角色

AI 在三个位置参与，边界写清楚：

| 位置 | 参与方式 | 默认状态 |
|---|---|---|
| 自然语言 → 规则 | **确定性中文解析器**（词典 + 模式匹配） | 启用。这是默认路径 |
| LLM 增强解析 | 可选插槽，检测到 `SENTINEL_LLM_KEY` 才启用 | **默认关闭** |
| 开发过程 | AI 编码助手参与脚手架、测试骨架、文档起草 | 见 `docs/AI-USAGE.md` |

**LLM 插槽的约束**：其输出必须通过同一套 Zod + 语义校验才被接受，永不被直接信任。

**AI 不生成投资结论。** 所有面向用户的结论句来自白名单模板，模板只接受
数值、名称、时点、来源这类事实字段。这是产品定位，不是实现细节。

开发过程中 AI 犯的错误与修正，逐条记在 [`docs/AI-USAGE.md`](docs/AI-USAGE.md)，
包括：把 HTTP 200 当成功、选了未开放的外部能力做事件源、臆造字段名、
把龙虎榜的小数当成百分数、降级时默认返回 false 等。

## 数据使用

### 当前模式：回放（默认）

**本作品未获得扶摇 API Key。** 因此默认使用确定性回放数据，无需任何凭据。

Fixture 由 [`tools/record-fixtures.ts`](tools/record-fixtures.ts) 于 **2026-10-15 收盘后**
从**公开免费行情源**抓取真实数值，再**重建成扶摇的信封结构**：

| 数据 | 真实来源 | 性质 |
|---|---|---|
| 行情快照 / 历史 K 线 / 估值 | 东方财富 `push2` / `push2his` | 抓取 |
| 交易日历 | 由沪深300 日 K 的真实交易日反推（国庆休市缺口真实可见） | 抓取 |
| 涨停池 | 东方财富 `push2ex`（36 只，含连板数/封板时间/炸板次数） | 抓取 |
| 热榜 | 东方财富人气榜 | 抓取 |
| 龙虎榜 | 东方财富 `datacenter-web` | 抓取 |
| 异动解读 / 异动监控 | 无免费等价源，按扶摇契约构造 | **构造** |

**数值是真实的**（如贵州茅台 2026-10-15 收盘 1312.97 元、涨幅 +2.10%），
但**信封是重建的**。详见 [`fixtures/README.md`](fixtures/README.md)。

这样做有两个目的：让回放数据有真实的数值形态；让扶摇适配器可被**真实契约**验证
（它消费的正是同一种结构与字段名）。

#### 字段名的契约对齐：逐字段核对过，并**列出未对齐的部分**

信封结构、端点路径、以及评测器**实际读取**的字段名，都逐条对照
[`docs/fuyao-contract.md`](docs/fuyao-contract.md)（契约原文存档）核实过：

| 已核实与契约一致 | 说明 |
|---|---|
| 信封 | `code` / `message` / `request_id` / `data.timestamp` / `data.item` |
| 快照 | `thscode` / `last_price` / `price_change_ratio_pct`（**已是百分数**）等 |
| 历史 K 线 | `date_ms` / `close_price` / `high_price` / `volume` 等 |
| 龙虎榜 | 列表键 `data.stock_items`、净买入 `net_value`、涨跌幅 `change`（**小数**） |
| 热榜 / 异动 | `rank` / `rank_change` / `heat`（上游给字符串）/ `tag_name` / `monitor_label` |

**但 fixture 里另有少量非契约字段，一并说明，不假装全是契约字段：**

| 字段 | 为什么存在 |
|---|---|
| `_source_explain_raw` | 东方财富龙虎榜的原始 `EXPLAIN`，是**合规陷阱的载体**（含「成功率44.94%」）。它模拟"数据源自带预测性文字"，用来验证出站净化确实会丢弃它（`TC-D5`）。真实扶摇响应不含该字段 |
| `_tag_code_mock` | **回放专用**：真实服务端按请求参数 `tag_codes` 过滤，响应只回展示名 `tag_name`；回放没有服务端，只能靠它模拟过滤。下划线前缀就是为了让它一眼可辨 |
| `trade_date` / `close_price` / `turnover_rate` / `billboard_deal_amt` | 从东方财富原始响应保留下来的字段，供界面展示；**评测器不读取**，因此不影响判定正确性 |

**一条被这套核对抓出来的真 bug**：`volume_ratio`（量比）曾被当作快照字段直读，
但契约的 `PriceSnapshotItem` **根本没有这个字段** —— 于是任何量比条件都恒判
`unknown` + `EMPTY_DATA`，功能等于没做。现已改为与 `drawdown_from_high_pct` 同路，
**从历史 K 线派生**（量比 = 当日成交量 ÷ 近 N 日平均成交量）。见
[`docs/AI-USAGE.md`](docs/AI-USAGE.md) 第 3.15 条。

#### 尚未对齐的四处（如实列出）

同一轮核对还查出四处**与契约不符的请求参数**。它们**只在实时模式下才会咬人**
（回放适配器忽略除 `thscode` 外的大部分参数），所以当前不影响任何判定结果，
本次**未修**，列在这里而不是假装不存在：

| 端点 | 问题 | 实时下的后果 |
|---|---|---|
| `prices/historical` | 缺必填的 `start` / `end`，且发了契约中没有的 `days` | 报 `code=1001` |
| `hot-stock-rank-trend` | 缺必填的 `start_date` / `end_date`，且发了非该端点的 `period` | 报 `code=1001` |
| `anomaly-analysis-stock` | 发 `thscode`，契约要求 `thscodes` | 报 `code=1001` |
| `abnormal-monitor-list` | 契约响应**不含** `data.timestamp`，而代码锚定它取数据时点 | 时点显示为「未知」 |

之所以现在不改：**没有 Key 就无法验证改对没有**，改了也只是把"未经验证的代码"换个样子。
实时适配器（见下文）实现时应当一并修掉这四处。

### 实时扶摇接入：**尚未实现**（如实说明）

**没有 `SENTINEL_MODE=live` 这回事。** 早先版本的 README 曾写"设 `SENTINEL_MODE=live`
即可切换到实时数据"，但代码里**根本不存在实时适配器** —— `src/server/sources/` 下只有
`replay` 与 `chaos`，全服务端没有任何出站 HTTP。那个环境变量只影响**显示文案**，
于是设了它就会把**回放数据标成"实时"**。这与本作品的立身之本（数据来源如实标注）直接冲突，
已删除该分支。

现在 `/api/health` 的 `mode` 与 `/api/meta` 的 `dataSource` 都来自**实际装配的适配器**，
而不是环境变量；冒烟测试第 ① 组会断言两者自洽，防止"假装实时"回归。
设了 `SENTINEL_MODE=live` 不会切换数据源，只会在启动时打印一条明确的告警。

**已实现的是契约层**，且这一层是真的：`envelope.ts` 按真实契约实现了信封解包
（`code` / `message` / `request_id` / `data.timestamp`）与全部 13 个业务错误码语义，
有 16 个单测覆盖；适配器接口 `SourceAdapter` 与端点表 `EP` 也已对照真实契约建立。
**未实现的是 HTTP 传输层** —— 没有凭据可用，写了也无法验证连通性，
所以没有写。它的接入点是 `SourceAdapter`：实现该接口即可与 `replay` 互换，
上层（调度、降级、证据链）无需改动。

### ⚠️ 已核实的端点约束

扶摇文档中有 **8 个能力标注「该能力暂未开放外部接入」**（已独立核实该措辞在正文出现 8 次）：
主力资金、资讯事件库、同花顺筹码形态、高频动向、市场成交额预测、
同花顺新增概念、宽基ETF申购净流入、期货F10宏观指标。

**这一条不需要相信我的转述。** 契约原文已逐字存档在
[`docs/fuyao-contract.md`](docs/fuyao-contract.md)（含来源 URL、抓取时间与字节数），
可以离线复核：

```bash
awk 'f{print} /^---$/{f=1}' docs/fuyao-contract.md | grep -c "暂未开放外部接入"
# → 8
```

**这直接决定了设计**：事件类条件**不能**走新闻事件库（`/api/news/events/search`），
必须落在仍然开放的外部端点上——异动解读、异动监控、龙虎榜、涨跌停池。
这些"未开放"能力保留在代码里并显式标注，用作 `CAPABILITY_DENIED` 降级场景的**真实依据**，
而不是凭空捏造一个失败场景。

## 已知边界

**解析能力**
- 是确定性词典+模式匹配，**不是模型**。超出词典范围的表达会如实报告"解析不了"，不会猜。
- 不支持主观描述（「走势健康」）与需要新闻语义的开放事件。
- 条件嵌套上限 3 层。

**数据**
- 回放 fixture 只覆盖 12 个标的（10 只个股 + 2 个指数）。查询范围外的标的会返回空数据并降级。
- 交易日历窗口固定为 `[今日-1年, 今日]`（与扶摇契约一致），无法查询更早的历史。
- 历史 K 线接口单次只服务单只标的、窗口 ≤ 10 年。
- 8 个未开放能力在真实数据模式下不可用（见上）。

**调度**
- 交易时段判定用的是固定时段（09:30–11:30、13:00–15:00）+ 交易日历，
  未处理临时休市与半日市。
- 非交易时段的价格条件仍会评估一次（规则可能针对收盘价），
  但新鲜度阈值放宽为"距最近一次收盘"，避免天天误报过期。

**并发与规模**
- 单进程。支持的任务量级是数百，未做分布式调度。
- 数据需求合并目前在同一 tick 内做，未做跨 tick 的请求缓存。

## 未做事项

- **实时扶摇接入（HTTP 传输层）**：契约层（信封解包、13 个错误码语义、端点表、字段契约）
  已按真实契约实现并有测试覆盖；但**实时适配器本体未实现**，因为无凭据可用、写了也无法
  验证连通性。数据源恒为回放，界面如实标注。详见上文「实时扶摇接入：尚未实现」。
- **邮件 / 微信 / IM 推送**：只实现了 Webhook 一种站外渠道，其余未接。
- **推送的异步投递**：站外投递是**同步**执行的——配了一个慢或挂掉的 webhook 会拖慢该次 tick
  （有 3 次尝试与单次 5s 超时上限）。未做独立的异步队列。默认未配置渠道，因此默认零开销。
- **多用户与鉴权**：当前是演示级单用户，无登录、无租户隔离。
- **关注池动态成员**：`watchlist` 类型在 DSL 中已定义，但目前按静态清单展开。
- **回测**：不做，且不在计划内——本产品只监控已发生的事实。
- **涨跌预测**：不做，且这是产品定位而非未完成项（见合规声明）。
- **iFinD MCP 接入**：它是登录后生成个人 MCP 地址的 SPA，必须后端做 MCP client，
  且同样需要账号，本次未接入。
- **移动端适配**：界面按桌面设计，窄屏可用但未优化。

## 合规声明

本产品**不预测涨跌、不承诺收益、不构成买卖建议**。

- 所有结论只陈述**已发生的事实**，并明确标注来源、时点、单位与统计口径。
- 结论分为**事实（fact）/ 推断（inference）/ 无法判定（unknown）**三级，界面区分呈现。
- 无法判定时明确说「无法判定」，**绝不静默给出"正常"结论**。
- 预测与建议类请求被直接拒绝并留痕，不产出任何规则。
- 数据源自带的预测性表述（如「成功率 44.94%」）在出站前被自动丢弃。

几个值得单独说的用例——它们守护的是最容易写错的地方：

- `TC-C5`：**HTTP 200 但 body 是网关 HTML 错误页 → 必须判为失败**。
  守护"HTTP 200 不等于业务成功"这条最容易被忽略的规则。
- `TC-C8`：龙虎榜的 `change` 是**小数**（`0.067927` = +6.79%），
  而价格的 `price_change_ratio_pct` **已是百分数**。不归一化会产生 100 倍的**假冲突**。
- `TC-D5`：龙虎榜 `EXPLAIN` 字段含「成功率44.94%」——**真实数据源自带的合规陷阱**，
  适配器必须丢弃。
- `TC-B1` + `TC-B5`：去重与恢复的边界，包括「改规则版本不应触发"条件已解除"」
  （换了阈值就是另一个条件）。

## 技术选型说明

| 选择 | 理由 |
|---|---|
| Node 24 + **`node:sqlite`** | 内置，**零原生编译**。`better-sqlite3` 在 Windows + 无构建工具链时容易卡住 |
